## Purpose

Give any model or coding harness one provider-neutral context packet for reviewing
AG-301 through AG-309. The prompt is intentionally self-contained at the scope
and rubric level, while its reference map uses progressive disclosure so a
reviewer reads the relevant source instead of loading every golden into context.

The prompt records the implementation tip that existed when it was written. A
reviewer must also capture the actual `HEAD` and working-tree diff; documentation
alignment changes after that tip are part of the review, not a reason to ignore
the worktree.

```text
TRACKED TICKET CONTRACT: REVIEW EVERY ROW

AG-301 — One production-oracle boundary
  Retain every stable persisted field needed to distinguish semantic graphs;
  justify normalized volatile fields; use total deterministic ordering; keep
  graph and query-envelope snapshots separate; ensure a newly added ToolMeta
  field cannot disappear silently; prove the oracle fails when meaningful data
  is tampered with. A digest may summarize private/large corpora but cannot
  replace committed synthetic goldens.

AG-302 — Production-pipeline harness
  Exercise the real LanguageRegistry -> Indexer -> SQLite ->
  GraphQueries/Astrograph composition through openProject. Pin root, clock,
  config, hashing, and lifetime. Support enriched and Pass-A-only modes. Keep
  test seams private and release resources in success and initialization
  failure. Reject an extractor-only simulation or a general DI framework.

AG-303 — JS/TS production goldens
  Cover TS, JS, TSX/JSX, enriched and Pass-A-only modes, multi-file resolution,
  stable IDs, resolved/external/unresolved/ambiguous states, and honest query
  envelopes. Pass-A-only must not claim compiler capabilities. External target
  persistence must be proved, not just an external edge label.

AG-304 — PHP production goldens
  Cover classes/interfaces/heritage/imported types and the accepted STEP 3
  receiver buckets: same class, parent, typed variable, and constructor-assigned
  property. Cover calls/new, external and unproven dynamic relations, display
  casing, grouped-use behavior, and enriched/Pass-A-only modes. No method-name
  fallback, cross-language healing, Magento XML/DI/plugins, generated-code
  semantics, or receiver inference beyond the accepted scope. If case-insensitive
  lookup or grouped-use behavior is still a known deviation, the oracle must
  expose rather than hide it.

AG-305 — Mixed-language ownership
  Homonymous JS/TS and PHP symbols remain distinct. Each eligible path has one
  owner. Changes in one backend cannot retarget the other. Backend disable must
  retire or classify only the affected facts and make completeness honest;
  re-enable must reconstruct clean normalized truth. No generic cross-language
  semantic bridge exists in 0.1.0.

AG-306 — Failure and honesty
  Cover oversized, unowned, disabled-backend, grammar initialization,
  extraction failure, unresolved/ambiguous relation, and capability-gap cases.
  Assert structured state/error/reason codes instead of prose. Unresolved
  targets never become node-shaped payloads, but material relational evidence
  remains visible. Prove at least one complete local answer inside a globally
  degraded project so the implementation cannot make every answer partial.

AG-307 — Four-route convergence
  Clean full, reused full, scanner sync(), and event-shaped syncFiles() must
  reach identical normalized files/nodes/edges/errors/envelopes for the same
  final source and config. Cover add/modify/delete/rename, eligible<->oversized,
  include/exclude, backend enable/disable, enriched/Pass-A-only, JS/TS, PHP,
  mixed, and promised recovery after interruption/failure. Routes consume one
  mutation script and isolated databases. Named event paths remain bounded
  unless config identity requires project-wide work. Include anti-vacuity and
  tamper checks.

AG-308 — Golden governance
  Updates require explicit validated fixture IDs, list every written path, and
  write deterministic JSON with a trailing newline. An unqualified update-all
  fails. Normal tests and CI are read-only. Every manifest has reviewed graph
  and envelope expectations. Extractor goldens and production goldens remain
  distinct and documented.

AG-309 — Independent review and exit gate
  Review the complete base...tip plus worktree, preserve findings and owner
  disposition, and reconcile canonical docs/deviations without inventing
  evidence. No unresolved P0/P1 oracle or convergence defect may remain. Stage
  closure additionally requires owner-run focused tests, full suite, typecheck,
  static check, docs check, build, binary smoke, and one reviewed targeted
  golden update in a disposable worktree. Until those results are recorded,
  the maximum verdict is READY_FOR_USER_VERIFICATION.

MANDATORY REVIEW AXES

1. Roadmap/harness alignment
   Verify AGENTS.md, ROADMAP.md, contracts, ADRs, architecture, review record,
   local tickets, code, and changelog describe one product. Identify stale or
   contradictory status, scope, version, evidence, language, LLM/document,

2. Oracle integrity
   Enumerate every transformation in normalize.ts. For each field say retained,
   canonicalized, sorted, root/path rewritten, omitted as volatile, or omitted
   incorrectly. Construct at least one counterexample for each omission class.
   Check total ordering, null versus absence, metadata, IDs, file outcomes,
   error codes, resolution state, confidence, provenance, capabilities,
   coverage, reasons, notes, evidence, truncation, and digest boundaries.

3. Production fidelity and ownership
   Trace one JS/TS, one PHP, one mixed, and one failure fixture from manifest and
   source creation through openProject, registry selection, Indexer phases,
   SQLite read-back, query probes, normalization, and expectation comparison.
   Verify test seams are private and production defaults are unchanged except
   for explicitly documented shipped behavior.

4. Assertion strength and matrix completeness
   Map every AG-303..307 required row to a concrete fixture, assertion, and
   golden/envelope. Look for weak predicates, OR conditions, vacuous
   convergence, a state accepted in place of another state, unasserted
   ambiguity candidates, missing external nodes, route-specific normalization,
   absent recovery, or fixtures that pass for the wrong reason.

5. Four-route convergence
   Verify routes start from isolated equivalent state, consume one mutation
   model, reach the requested final source/config, compare the complete oracle,
   and cannot converge trivially. Check event-scope boundedness and config-wide
   exceptions. Ensure each route is compared with clean truth rather than with
   another potentially wrong route.

6. Failure and query honesty
   Verify lifecycle completion is distinct from extraction trust; disabled,
   unowned, oversized, grammar, extraction, capability, unresolved, and
   ambiguous cases remain attributable. Check local/global query domains and
   positive/negative trace behavior. Ensure unresolved targets are not shaped
   as nodes while blocker evidence survives filtering.

7. Golden governance and determinism
   Verify normal tests cannot write, update-all is rejected, identifiers are
   validated, only named fixtures change, generated output is deterministic,
   every manifest has expectations, and CI has no ambient update mode. Inspect
   representative goldens deeply and use invariant tests to sample the rest.

8. Maintainability and quality
   Review depth of interfaces, duplication, hidden coupling, resource ownership,
   failure cleanup, test-only abstraction leakage, fixture readability,
   misleading names/comments, formatter/lint coverage, and whether the harness
   is maintainable enough to guard 0.1-D rather than becoming its own system.

9. Documentation/evidence honesty
   Verify every AS-IS statement names current source and every TO-BE statement
   has an accepted owner. Reconcile the Round 1/2/3 claims in 0.1-c-review.md
   against current code. Verify CHANGELOG and deviations reflect deliberate
   shipped behavior changes. Ensure user-run evidence remains visibly pending
   where it has not been supplied.

10. Diff hygiene
    Attribute every committed and uncommitted change to a ticket, review fix,
    or explicit roadmap/harness alignment change. Flag generated noise,
    unrelated behavior, stale files, accidental public exports, or user changes
    that would be overwritten. Do not edit or commit during this review.

Severity:
  P0 = corrupts/deletes truth, fabricates a resolved answer, makes the oracle
       unable to detect semantic divergence, or creates unsafe source/release
       behavior.
  P1 = materially incomplete ticket/contract, dishonest completeness, major
       matrix hole, convergence gap, or lifecycle leak that blocks 0.1-C.
  P2 = bounded weakness or maintainability defect that should be scheduled but
       does not invalidate the stage oracle.
  P3 = documentation, naming, hygiene, or low-risk precision issue.

maintenance consequence. Do not convert known 0.1-D performance work or 0.2

   Confirm or challenge the canonical roadmap, AstroDocs boundary, CodeGraph/
   Graphify reference policy, 0.1-D gate, 0.2 language order, source precedence,
   and portability of local versus tracked documents.

3. Findings
   Ordered P0 -> P3, using the finding standard above. If none, say none and
   give the counterexamples attempted.

4. Ticket matrix AG-301..AG-309
   For each: implemented evidence, acceptance gaps, documentation evidence,
   owner-run evidence state, and verdict pass/partial/fail/not verifiable.

5. Required-matrix traceability
   Map each language/failure/mutation/mode row to fixture, assertion, golden or
   envelope, and relevant canonical documentation.

6. Prior-review audit
   For every Round 1/2/3 finding in 0.1-c-review.md: fixed and held by a strong
   regression, partially fixed, stale claim, accepted debt, or still open.

7. Uncommitted-change audit
   Explain every `git diff HEAD` file and whether it is correct, incomplete,
   unrelated, or conflicts with the committed stage.

8. Residual risks and maintainer questions
   Separate accepted later work from decisions that need an answer. Never fill
   in a missing maintainer decision.

9. Owner-run verification plan
   Exact commands in the safest useful order, expected evidence to capture,
   and which ticket/gate each command supports. Do not claim they ran.

10. Inspected areas with no finding
    Name the files/symbols and the invariant checked so review coverage is
    auditable.

Return one coherent report, not nine disconnected summaries. Optimize for
evidence and decision usefulness, not agreement with the implementation author.
```

## Maintenance

Update the expected implementation tip and ticket mapping only when the 0.1-C
series is rewritten. Later documentation-only alignment commits do not change
the review base; the prompt already requires inspection of the actual complete
range and working tree. If stage acceptance changes, update the ticket contract
here and the corresponding canonical stage record together.
