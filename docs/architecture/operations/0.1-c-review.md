## Round 2 findings and their disposition

Four audits: the oracle's transformations, assertion strength in the JS/TS and PHP fixtures, the
disabled-backend ownership gap, and harness/matrix/governance over-claiming. Two audits
independently found the same non-total edge order, which is why it is treated as confirmed rather
than as one model's opinion.

### Product defects found by building the oracle

| # | Severity | Defect | Fix |
|---|---|---|---|
| R2-1 | **P1** | **A disabled backend left no evidence.** The scanner's extensions came from `registry.allExtensions()`, which omits a disabled backend, so no `.php` path was scanned; membership classified the persisted path `out_of_scope` rather than `backend_disabled`, and `out_of_scope` is not recordable. Rows were deleted and **every query answered `partial: false`** over a project half of which was unindexed. `classifyPath` and `eligibilityEvidence` had implemented the honest path all along; nothing could reach it. | `openProject` builds the scanner from every shipped backend's extensions, enabled or not. Parsing is unchanged — such a file is recorded with zero nodes and reaches no parser. |
| R2-2 | **P1** | **The harness was not hermetic, and it made a wrong answer look right.** `ts.createProgram` had no `types`/`typeRoots`, so TypeScript resolved automatic `@types` from the *process* working directory — this repository — pulling `bun-types` and `@types/bun` into every fixture. `import { join } from "node:path"` in a dependency-less project came back `external`/`high` instead of `unresolved`/`low`, so a fixture asserting that an unprovable target stays unproven passed because the harness had made it provable, and the goldens encoded this checkout's installed types. | Every temporary root gets `HERMETIC_TSCONFIG` (`types: []`, `typeRoots: []`). Module resolution is untouched, so a package installed inside a fixture's own root still resolves. |

### Oracle defects

| # | Severity | Defect | Fix |
|---|---|---|---|
| R2-3 | **P1** | `normalizePath` trimmed at the first `/node_modules/` *before* removing the root, so `<root>/packages/a/node_modules/x` and `<root>/packages/b/node_modules/x` — two distinct declarations in a monorepo — normalized to one path. | Root removal runs first; the `node_modules` fallback applies only to a path still absolute afterwards, i.e. genuinely outside the project. |
| R2-4 | **P1** | `stripRoot` was an unanchored `replaceAll` over free text. With a root of `/tmp/ag`, `"in /tmp/agent/x.ts"` became `"in ent/x.ts"` — byte-identical to a genuinely different diagnostic. | The bare-root replacement is anchored to a path boundary, so a sibling directory survives while `<root>: reason` is still stripped. |
| R2-5 | **P1** | `compareEdges` claimed to be a total order and was not: `metadata` is `retained` but absent from the comparator, so two `ambiguous` edges differing only in their candidates were tied and ordered by SQLite row order. | Canonicalized `metadata` is the final key. |
| R2-6 | **P2, rejected** | `omitUndefined` recursing into `metadata` was reported as destructive: `{candidate: undefined, count: 1}` and `{count: 1}` compare equal. | **Not changed.** `metadata` is persisted as JSON and `JSON.stringify` omits `undefined` object values, so SQLite cannot hold that difference; preserving it would make an in-memory graph diverge from the identical graph read back out. The rule is now stated in the module: this oracle compares *persisted* meaning, and a distinction SQLite cannot store is not a distinction. A meaningful absence must be `null`, which is preserved. |

Each of R2-3 through R2-6 has a regression test in `normalize.test.ts` built from the audit's own
counterexample.

### Falsely positive coverage

| # | Severity | Finding | Fix |
|---|---|---|---|
| R2-7 | **P1** | `jsts-enriched` produced **no `unresolved` edge at all** — only `resolved`, `external` and `ambiguous` — while AG-303's matrix requires unresolved evidence. The test that claimed to cover it asserted `resolutionState !== "resolved"`, which accepts `external`, and was in fact observing the leak in R2-2. | `src/unprovable.ts` adds a call on an `any` receiver and a non-literal `import()`. The fixture now exercises all four states, and the assertions name the exact state, the null target and the `low` confidence. |
| R2-8 | **P1** | The PHP receiver-bucket test keyed a `Map` by `targetName`, collapsing the three distinct receivers that all call `run()` onto one entry: it verified whichever edge came last and would have passed with two of three buckets broken. | Filter and count all three, assert every one resolved and that all three land on a single target. |
| R2-9 | **P2** | The merged-declaration test never asserted the `ambiguous` edge AG-303 requires — a regression that silently picked one candidate would have passed. | Assert the state, the retained target and that `metadata.candidates` is exactly the two declarations. |
| R2-10 | **P2** | Six vacuous assertions: `expect(xs.every(p)).toBe(true)` and `expect(xs.filter(p)).toEqual([])` are satisfied by an empty `xs`. The Pass-A subset check, the PHP scalar and bare-name checks, and three in `mixed.test.ts` — including the disable test, where "PHP facts are gone" was provable against a PHP half that had never produced any. | A positive guard precedes each. |
| R2-11 | **P2** | The AG-307 vacuity guard waived its cross-file requirement per *row* on an OR over both languages, so a mixed row with one Pass-A-only backend would have waived it for the enriched half too. | Gated per backend. |
| R2-12 | **P2** | `update-goldens.test.ts` checked manifest → file but not the reverse, so a renamed fixture would leave an orphan golden that nothing verifies. | A reverse check over `__goldens__`. |
| R2-13 | **P3** | `biome.json` exempted the whole fixture tree, leaving the new directory unlinted (found in round 1, repeated here). | Narrower override; nineteen findings fixed. |

### Judged and left alone

- **7 of 18 route rows do not add event-scoping coverage** beyond `reused-full`/`scanner-sync`,
  because a configuration change is project-wide by contract and their derived batch is empty. That
  is AG-307's documented Work item 5, tested directly, and not a defect.
- **`compare.ts` misattributing which duplicate changed** when two edges tie: real, but `assert.ts`
  runs `toEqual` as a backstop, so it cannot pass silently — only produce a confusing diff. Fixing
  R2-5 removes the tie that causes it.

## Residual risks

1. **The goldens were recorded by the implementing agent.** They pass and their invariants are
   asserted independently of the JSON, but no human has read all 32 files. The per-fixture
   invariant tests exist precisely so that review can be sampled rather than exhaustive; the review
   expectations in [Testing and evaluation](testing-and-evaluation.md#review-expectations) say what
   to look for.
2. **Finding B (`DEV-009`) is an unfixed product gap**, pinned by a golden. Finding A is now fixed
   (R2-1), but its *reason* is imprecise: a disabled backend surfaces as `coverage_incomplete`
   rather than a capability limit, because `registry.summary()` lists only constructed backends and
   `capabilityReasons` therefore cannot see a disabled one. Closing that needs a
   shipped-but-disabled capability table, which is `DEV-004`/`NEW-002` work rather than 0.1-C's.
3. **Runtime.** The pipeline suite adds roughly 35 seconds on an unloaded machine, and about four
   times that under contention. The explicit timeouts are generous rather than tight.
4. **No real-repository evidence.** `digest()` exists for the corpus that cannot be committed, and
   nothing has used it yet. That path belongs to `DEV-009`'s certification scenario and `NEW-008`.
5. **`bun run check` is red at the baseline** (finding E), so it cannot serve as a gate for this
   stage until those 22 pre-existing findings are dispositioned.

## Exit gate

Unmet until the owner reports results.

- [ ] `bun test` — run and reported by the owner
- [ ] `bun test packages/core/__fixtures__/pipeline` — run and reported by the owner
- [ ] `bun run typecheck` — run and reported by the owner
- [ ] `bun run check` — run and reported by the owner, with the 22 pre-existing findings dispositioned
- [ ] `bun run docs:check` — run and reported by the owner
- [ ] `bun run build` plus binary smoke — run and reported by the owner
- [ ] The reviewed golden update performed once in a disposable worktree
- [ ] Finding B and the imprecise-reason residue of R2-1 explicitly accepted or scheduled
- [ ] Finding C's seam explicitly accepted or rejected
- [ ] `DEV-014` moved to `closed`, citing the owner's commands and results

Only then is 0.1-C closed. The handoff to 0.1-D is narrow: **performance work may change how the
pipeline spends memory and CPU, and may not change what it persists or what it claims.** The
eighteen-row four-route matrix and the seventeen production goldens are the instrument that decides
that, and an optimization that requires re-recording a golden is a behaviour change until proven
otherwise.

## Verdict

**READY_FOR_USER_VERIFICATION.** AG-301 through AG-308 have implementation and canonical-document
evidence, and the oracle and the convergence matrix are green.

Round 2 found six P1s that round 1 did not, five of them in work round 1 had already called clean —
two product defects, three oracle defects, and a JS/TS matrix row that was passing for the wrong
reason. All are fixed with regression tests. That is the honest reading of this stage's maturity: the
oracle now catches what it is for, but it took two rounds to get there, and the second round's
themes came from outside this session. `DEV-014` stays open, and 0.1-C stays open, until the owner
supplies the commands above and disposes of finding B, the R2-1 residue, and finding C.
